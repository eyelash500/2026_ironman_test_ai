# spec — 規格考古產物

受測物上線一年，沒有 PRD、沒有需求文件、沒有驗收條件。

這個目錄記錄的不是「它應該怎麼做」，而是**「程式碼已經替使用者做了哪些決定，而沒有人做過那些決定」**。

方法見系列 Day 8。

十個裡只有三個對應到已知缺陷。其餘七個現在「沒有壞」，但也沒有人能說它是對的。

**缺陷 B 和 A′ 不在這裡**——它們不是規格問題，是實作沒做好。
壽命填反了要不要擋，跟「退休那年算不算支出」不是同一種問題：
前者有標準答案，後者需要有人拍板。

## 四種性質

| 性質 | 意思 | 處置 |
|---|---|---|
| 沉默決定 | 程式做了選擇，而且看起來像是語法選擇（例如迴圈從 1 開始） | 寫成規格條款，精確到索引 |
| 歧義 | 兩種以上做法都說得通，選哪個會改變使用者看到的數字 | 交閘門 1 裁決 |
| 假設 | 與現實有明確落差，但不確定是刻意簡化還是沒想到 | 裁決並在文件標明落差 |
| 已知缺陷 | 第一幕已解剖過，機制清楚 | 直接補齊規則 |

## 檔案格式

每一條都是同一個格式：程式碼座標 → 現有實作 → 隱含假設 → 待裁決選項 → 裁決。

**「待裁決」的選項可以由 AI 列，「裁決」那一欄不行。**
那是產品決定，不是程式決定。

## 狀態

裁決結果見 Day 9 與根目錄的 `decisions.md`。裁決完成後，
每一條會對應到一則 `PRD-xx`，成為 Day 30 修復版的唯一依據。
