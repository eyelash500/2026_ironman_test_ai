# generated/ — AI 呼叫的原始輸出

系列的核心實驗是「AI 產的測試有多好」。任何分數都必須能回溯到產生它的那批輸出，
否則只是印象。這個目錄就是那批輸出。

## 結構：以「實驗」為單位

```
generated/
└── YYYY-MM-DD-<dayNN>-<實驗代號>/
    ├── manifest.yaml     跑之前先寫
    ├── prompt.md         逐字的 prompt，不節錄
    ├── run-01.txt        原始輸出，一個字都不改
    ├── run-02.txt
    └── ...
```

實驗代號範例：`2026-09-20-day22-L1-gemini`、`2026-09-16-day20-golden-mutation`。

## manifest.yaml

```yaml
experiment: day22-L1-gemini
datetime: 2026-09-20T14:32+08:00
model: gemini-2.5-pro          # 實際版本字串，不是「Gemini」
params:
  temperature: 1.0
  top_p: 0.95
runs: 5
prompt: prompt.md
notes: 第 3 次輸出被截斷，已重跑；兩份都留
```

## 三條紀律

1. **原始輸出一個字都不改。** 需要清理格式時另存 `run-01.cleaned.txt`，不覆蓋原始檔。
2. **失敗的、被截斷的、看起來很蠢的都留著。** 刪掉就是選擇性報告——會不知不覺只留下
   支持結論的那幾份。
3. **manifest 在跑之前寫。** 跑完才補，容易變成照結果反推當初的設定。

## 為什麼

- **鐵律要求任何分數 ≥5 次生成報分佈。** 五次就是五份輸出，不存檔就沒有分佈可談。
- **模型會改版，而且不會通知你。** 三個月後同一個 prompt 給不同答案是一定會發生的。
  存檔換來的不是**可重現**（做不到），是**可查證**——別人不能重跑出你的結果，
  但可以檢查你手上那批輸出是否支持你的結論。
- **反例已經發生過。** 系列 Day 2 的初稿引用了一段加引號的 Gemini 對話，因為沒有存檔，
  必須翻 iThome 原文才能證明那是捏造的。有這個目錄，六十秒就查完。

## 何時開始用

首次實際呼叫 API 時（預計 9/12 的 Gemini spike）。在那之前此目錄只有本說明。
